# Domain: Order Management

Specification of the domain implemented in this repository: business rules, entities, events and error
contract, as the source of truth independent of implementation detail. Same domain as
[`fastapi-order-api`](https://github.com/ronybrand/fastapi-order-api) (the specification this project was
built from), [`spring-order-api`](https://github.com/ronybrand/spring-order-api) and
[`nest-order-api`](https://github.com/ronybrand/nest-order-api), implemented here on ASP.NET Core, EF Core
and PostgreSQL. See the README for stack-specific detail.

## 1. Overview

```
Customer (1) ──< Order (1) ──< Item
```

- **Customer:** customer registration data.
- **Order** (aggregate root): a customer's order, with a list of items and a calculated total.
- **Item:** order line (free text description, no product catalog).

Out of scope: payment, inventory, product catalog, shipping.

## 2. Entities

### Customer

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | generated by the database |
| `name` | string | required, not blank |
| `tax_id` | string | required, **unique among active customers**, pattern `^[A-Za-z0-9./-]{5,20}$` |
| `passport_number` | string | optional, **unique among active customers** when present, pattern `^[A-Z0-9]{6,9}$` |
| `email` | string | required, valid e-mail address |
| `created_at`, `updated_at`, `created_by`, `updated_by` | | audit (user subject or `system`) |
| `deleted_at`, `deleted_by` | | soft delete (null means active) |

`tax_id`, `passport_number` and `email` are PII: never returned by the API, never logged in plaintext.

### Order (aggregate root)

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | generated by the database |
| `customer_id` | UUID | required, must reference an active customer |
| `items` | list of Item | composition, lifecycle tied to the order, at most 200 |
| `total` | decimal | **derived**, `Σ unit_price × quantity` over the current items |
| `status` | `OPEN`, `CONFIRMED`, `CANCELED` | default `OPEN` |
| `version` | integer | optimistic concurrency token (Postgres `xmin`) |
| audit and soft delete | | same as Customer |

### Item (child of Order)

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | generated by the database |
| `order_id` | UUID | required |
| `description` | string | required, not blank, at most 255 characters |
| `unit_price` | decimal | required, `> 0`, at most 2 decimal places |
| `quantity` | integer | required, `> 0` |

Item subtotal is `unit_price × quantity` (computed, not persisted). Identity is the `id`, not the
description: descriptions can repeat within one order.

## 3. Order status

```
OPEN ──> CONFIRMED ──> CANCELED
OPEN ──────────────> CANCELED
```

- `OPEN`: items can be added, changed and removed. May go to `CONFIRMED` or `CANCELED`.
- `CONFIRMED`: items are frozen. May only go to `CANCELED`.
- `CANCELED`: terminal.

## 4. Business rules

1. **Total calculation:** recalculated after any item creation, update or removal.
2. **Items are editable only while `OPEN`:** otherwise `VALIDATION-02`.
3. **Confirm** (`OPEN` to `CONFIRMED`): fails when the status is not `OPEN` (`VALIDATION-04`) or when the
   order has no items (`VALIDATION-03`).
4. **Cancel** (`OPEN` or `CONFIRMED` to `CANCELED`): fails when already canceled (`VALIDATION-08`).
5. **Create order:** requires an existing customer (`VALIDATION-07`); builds the items and the initial total.
6. **Item limit:** at most 200 items per order.
7. **Customer uniqueness:** `tax_id` (`CONFLICT-01`) and `passport_number` when provided (`CONFLICT-02`).
   A blank passport number does not count. Values of a soft-deleted customer are released for reuse.
8. **Customer deletion blocked:** a customer with any non-deleted order cannot be deleted (`CONFLICT-03`).
   Soft-deleted orders do not count.
9. **Delete is always soft delete:** records with `deleted_at` set are excluded from every default query.
10. **Optimistic concurrency on Order:** conflicting concurrent mutations fail with `CONFLICT-00` and never
    silently overwrite each other.

## 5. Domain events

### OrderStatusChangedEvent

Fired at the end of `confirm` and `cancel`, only when the customer has a non-blank e-mail.

| Field | Type |
|---|---|
| `order_id` | UUID |
| `customer_email` | string |
| `customer_name` | string |
| `old_status` | string |
| `new_status` | string |
| `total_amount` | decimal |
| `changed_at` | datetime |

Published to RabbitMQ right after the status change commits, as a best-effort publish (see
[ADR 0002](./docs/adr/0002-no-transactional-outbox.md)). A separate worker process consumes the queue and
sends the e-mail through SMTP, retrying transient failures before routing to the dead-letter queue.

## 6. Domain errors

**Validation (400):** invalid request body, order not editable, confirming an empty order, invalid status
transition, invalid filter value, unknown sort field, nonexistent customer on order creation, canceling an
already canceled order.

**Not found (404):** customer, order, item.

**Conflict (409):** concurrent modification, duplicate `tax_id`, duplicate `passport_number`, deleting a
customer with orders.

**Rate limit (429):** too many requests. **Other:** unexpected error (500).

The authoritative, versioned code table is in the README's "Error catalog".

## 7. Use cases

### Order
- `create(customer_id, items[])`: creates an `OPEN` order with the calculated total.
- `get(id)`, `delete(id)` (soft delete).
- `add_item`, `update_item_quantity`, `remove_item`: require `OPEN`, recalculate the total.
- `confirm(id)`: `OPEN` to `CONFIRMED`, requires items, publishes `OrderStatusChangedEvent`.
- `cancel(id)`: `OPEN` or `CONFIRMED` to `CANCELED`, publishes `OrderStatusChangedEvent`.
- `search(filters, sorting, pagination)`.

### Customer
- `create`, `update`, `delete`: require role `admin`; uniqueness validated (excluding the record itself on
  update); delete is blocked while there are orders.
- `get(id)`, `search(filters, sorting, pagination)`.

## 8. Reference endpoints

See the README's "Endpoints" section. Every mutating route on `/customers` requires the `admin` role; every
`/orders` route and the read routes on `/customers` only require an authenticated user. A missing or
invalid token returns `401`; a valid token without the required role returns `403`.
