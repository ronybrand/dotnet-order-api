# Instructions for code agents in this repository

Clean Architecture on .NET 10 (`Domain`, `Application`, `Infrastructure`, `Api`, `Worker`). The domain
specification lives in `README.md` (same domain as `fastapi-order-api`). Read the closest existing domain
(`Customer` for simple entities, `Order` for aggregates with children and cross-domain side effects) and mirror
its structure before adding or changing anything.

## Before writing code

- Classify every new field against PII, special category data, PCI, financial data and secrets. Sensitive fields
  use `[Sensitive]` (`SensitiveJsonModifier` for serialization, `SensitiveMasker.Mask` for logging); never an
  ad hoc solution, and never add a sensitive field "just in case".
- Apply DRY in production code and in tests.
- Decide explicitly whether a new side effect should be asynchronous (RabbitMQ producer + worker) or a simple
  synchronous call, and write the reason in the README.

## TDD (red, green, refactor)

- Write the test, run it and see it fail before the production code.
- `Test/OrderApi.Test` covers every relevant branch of a service: happy path, not found, uniqueness conflict,
  violated business rule and, when applicable, optimistic concurrency.
- Every HTTP domain has integration tests (`Test/OrderApi.IntegrationTest`) with at least one 401/403 per
  protected endpoint. Never relax rate limiting, CORS, headers or body limits to make a test pass.

## Entities and persistence

- `Guid Id` generated by the database (`HasDefaultValueSql("gen_random_uuid()")`), never `Guid.NewGuid()`.
- Soft delete (`ISoftDeletable`) for aggregate roots; unique indexes are filtered by `deleted_at IS NULL`.
- No navigation properties between entities, only scalar foreign keys. Children inside an aggregate are a
  `List<T>` loaded by the repository.
- Every uniqueness check in a service has an equivalent unique index, and the violation is translated to a
  `ConflictDomainException`.
- Concurrency token (`xmin`) on entities with real concurrent writes.
- Migrations are generated with `dotnet ef` and reviewed by hand (`Down()` complete; remove the generated
  `xmin` column from `CreateTable`).

## Services, controllers and authorization

- Every action declares `[Authorize]` or `[Authorize(Roles = Roles.Admin)]` explicitly; role names are constants.
- Business rules throw `NotFoundDomainException`, `ValidationDomainException` or `ConflictDomainException` from the
  service; controllers never catch or build error responses. Error codes follow the existing catalog and are never
  reused for another meaning.
- Validation runs through the global `ValidationFilter`; controllers never inject validators.
- Resources owned by a specific user validate ownership in the service through `ICurrentUserAccessor` and answer
  `404`, never `403`.
- Search, filter and pagination reuse `SearchExecutor`; fields are resolved from EF metadata.
- Use `string.IsNullOrWhiteSpace`, `is { Count: > 0 }` and named positive properties such as `IsEditable`
  instead of negations.

## Security baseline (never disable by accident)

Security headers, rate limiting, request body limit, JWT `aud`/`iss`/RS256 validation, the production CORS
fail-fast guard, Swagger only in Development, no secrets in source or migrations, and no sensitive data in logs.

## Definition of done

- `make verify` (format, build with warnings as errors, unit and integration tests, coverage gate) is clean; every suppression is
  documented.
- `dotnet test src/Test/OrderApi.Test` was run; integration tests were run when Docker is available. Rule out
  Docker/Testcontainers problems before concluding that the implementation is wrong.
- No new code uses an `[Obsolete]` API of the resolved dependency versions.
